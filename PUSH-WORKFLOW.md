# Промпт: как пушить MySavdo в GitHub

Вставь это как первое сообщение новому ИИ-чату, когда попросишь его сделать пуш
(«сделай пуш», «я добавил новые фичи, запушь» и т.п.). Ниже — всё, что нужно
знать, чтобы не наломать дров.

## Архитектура: два раздельных места

- **`mysavdo`** (или похожая папка вроде `mysavdo_v7_nocomments\mysavdo`) —
  рабочая копия, **НЕ git-репозиторий**. Здесь пользователь (и ИИ) правит код.
- **`mysavdo_adaptive`** — папка **рядом** с рабочей (тот же родитель на диске).
  Это настоящий git-репозиторий, `origin` → `https://github.com/Sherhan000/mysavdo.git`,
  ветка `main`. Именно её пушат.

Сначала найди обе папки (они лежат рядом друг с другом на диске — если не
знаешь пути, поищи `mysavdo_adaptive` рекурсивно от `C:\Users\<user>\`).

**Важно:** пользователь иногда коммитит и пушит в `mysavdo_adaptive`
**напрямую сам**, через свой терминал, независимо от ИИ-сессий. Поэтому
**никогда не считай**, что `origin/main` там же, где ты его оставил в прошлый
раз — всегда сначала `git log --oneline -5` и `git status` в `mysavdo_adaptive`,
прежде чем что-либо делать.

## Порядок действий

### 1. Найди, что реально изменилось

Не доверяй поверхностному `diff <(ls A) <(ls B)` — из-за кириллицы в пути
(`Шерчахон Шукуроа`) построчные `grep`/`diff` с интерполяцией пути иногда
молча теряют совпадения. Надёжнее:

```bash
for item in file1 dir2 ...; do
  [ -e "$A/$item" ] && [ -e "$B/$item" ] && echo "$item: в обеих" 
  [ -e "$A/$item" ] && [ ! -e "$B/$item" ] && echo "$item: НОВОЕ, надо смотреть"
done
```

Проверь отдельно: верхний уровень обеих папок, `backend/api`, `backend/config`,
`assets/js`. Если появилась новая директория (например было с `mobile/`,
`ig-private-service/`) — не копируй её вслепую, сначала прочитай, что внутри.

### 2. Синхронизация (robocopy /MIR)

Запускай **по одной команде за раз** в PowerShell — комбинирование
robocopy + Copy-Item + if-блоков в одном вызове иногда даёт странные ошибки
парсинга.

```powershell
$A = "...\mysavdo"
$B = "...\mysavdo_adaptive"
robocopy "$A\assets"  "$B\assets"  /MIR /NFL /NDL /NJH /NJS
robocopy "$A\backend" "$B\backend" /MIR /NFL /NDL /NJH /NJS
```

Exit-коды robocopy 1/2/3 — это **успех** (файлы скопированы / лишние удалены /
и то и то), не ошибка. Ошибка — это когда в тексте вывода реально `ERROR`.

Отдельные топ-level файлы (`index.html`, `admin.html`, `.htaccess`, и что там
ещё появится — `offline.html`, `sw.js`, `codemagic.yaml` и т.п.) `/MIR` не
трогает — их надо copy-item поштучно, и список нужно **перепроверять каждый
раз** (сравнивая топ-level листинг), потому что он растёт.

**После каждого robocopy assets** — `assets/img/uploads/.gitkeep` может
исчезнуть (в рабочей папке его нет, `/MIR` удаляет лишнее в приёмнике).
Пересоздай пустым файлом.

**`mobile/`** (Capacitor Android+iOS) — там 200+ МБ мусора сборки. Копируй с
исключениями:
```powershell
robocopy "$A\mobile" "$B\mobile" /MIR /XD node_modules .gradle .kotlin build build-output Pods DerivedData xcuserdata .cxx capacitor-cordova-android-plugins /XF "*.keystore" "*.apk" /NFL /NDL /NJH /NJS
```
После — должно остаться ~4 МБ, не сотни. Проверь `du -sh` и что не затесались
`.keystore`/`.apk`/`node_modules`.

**`.env` и `.env.example`** — `.env` **никогда** не копируется и не коммитится
(секреты). `.env.example`/`.gitignore` в `mysavdo_adaptive` не синхронизируются
автоматически — если рабочая копия завела новые переменные окружения, вручную
слей их в `mysavdo_adaptive/.env.example` (просто добавь недостающие строки,
не затирай их специфичные докер/Traefik-переменные). Если появилась новая
подсистема с новым `.env`-требованием — не забудь и `mysavdo_adaptive/.env`
(реальный, локальный, некоммитящийся) обновить, иначе фича будет молча
падать с «не настроено».

### 3. Проверки перед коммитом — ОБЯЗАТЕЛЬНО

```bash
# PHP — все файлы, без исключений
while IFS= read -r -d '' f; do
  php -l "$f" 2>&1 | grep -q "No syntax errors" || echo "FAIL: $f"
done < <(find "$A/backend" -name "*.php" -print0)

# JS
node --check "$A/assets/js/app.js"
node --check "$A/assets/js/admin.js"
# + любые новые .js файлы

# CSS — баланс скобок
node -e "const s=require('fs').readFileSync('$A/assets/css/style.css','utf8'); let d=0; for(const c of s){if(c==='{')d++; if(c==='}')d--;} console.log(d);"
```

**Отладочные огрызки** — грепни на `console\.log\(|var_dump|print_r\(|HTTP Code:|debugger;` —
уже дважды находил забытые debug-строки, которые либо ломали нормальные
сообщения об ошибках, либо утекали внутренние ответы клиенту. Если нашёл —
почисти перед пушем, не пуши как есть.

**Секреты** — грепни диф и новые файлы на паттерны ключей/паролей/токенов
(`api[_-]?key\s*[:=]\s*['"][a-zA-Z0-9_-]{15,}`, `bearer [a-zA-Z0-9_.-]{20,}`,
`AIza...`, `-----BEGIN...PRIVATE KEY-----` и т.п.). `.env` может «поменяться на
диске» между твоими чтениями — это нормально, просто НИКОГДА не копируй его
содержимое в закоммиченный файл.

**Мусорные/подозрительные файлы** — если видишь файл вроде `test.py` с
бессмысленным содержимым (не относящийся к проекту черновик) — не пуши,
это шум. Если видишь файл вроде `*-reset-once.php`/`*-debug.php` с явным
намёком в названии или в самом коде («удали меня после использования»,
без аутентификации на эндпоинте) — **спроси пользователя**, включать ли его,
не решай сам молча в любую сторону.

**Пропавшие директории/подсистемы** — если что-то крупное исчезло из рабочей
копии (был Node-сервис/интеграция — и нет), но в `mysavdo_adaptive` оно ещё
есть с прошлого раза — **не удаляй молча**. Спроси, что случилось, прежде чем
чистить связанные куски (docker-compose сервисы, .env-переменные и т.д.).

### 4. Коммит и пуш

```bash
cd "$B"
git add -A
git status --porcelain   # финальная проверка перед коммитом
git commit -m "человеческое summary на русском, что реально добавилось"
git push origin main
git status                # должно быть "nothing to commit, working tree clean"
```

Если по пути открывал тестовый `php -S`/`node` сервер — обязательно убей его
и удали тестовые записи из БД **до** финального ответа пользователю (фоновые
процессы между отдельными вызовами инструмента не убиваются сами, `kill %1`
не сработает в новом вызове — ищи процесс по порту через
`Get-NetTCPConnection -State Listen | Where LocalPort -eq <port>` и
`Stop-Process`).

## Философия

Пользователь пишет код сам (иногда через другие ИИ-инструменты, иногда сам
руками) и просто просит «запушь». Твоя работа — не слепой `git push`, а:
1. Понять, что реально изменилось.
2. Прогнать базовые проверки (синтаксис, секреты, мёртвый код).
3. Заметить то, что явно не должно ехать в прод молча (одноразовые скрипты,
   мусорные файлы, полдороги сделанные фичи) — и спросить, а не решить самому.
4. Только после этого — коммит с внятным сообщением и пуш.

Если сомневаешься — лучше на 30 секунд задать уточняющий вопрос, чем
запушить то, что сломает прод или утечёт секрет.
